# 委譲ブリーフの雛形とレビュー手順

委譲の品質は**ブリーフの質**でほぼ決まる。受け入れ基準を先に固定すると、レビューが安くなり
往復が減る=トークンが減る。

## 委譲ブリーフの雛形(subagent の prompt に入れる)

```
## ゴール
<何を作る/変えるか。一文で>

## 対象範囲
- 触ってよい: <ファイル/ディレクトリを明示>
- 触ってはいけない: <明示。範囲外の改変を防ぐ>

## このリポジトリの前提(まず読め)
- <規約ファイルのパス。例: CLAUDE.md / .claude/skills/<x>/SKILL.md / knowledge/voice.md>
  ※ 全文は貼らない。パスを渡して subagent 自身に読ませる(その読解トークンは親に返らない)

## 受け入れ基準(すべて満たすまで直してから報告)
- [ ] <検証可能な条件を箇条書き>
- [ ] <...>
- [ ] 範囲外のファイルを変更していない

## 既存テストの扱い
- 目的を変えない追従(実装変更に合わせたアサーション文字列・スタブ変数の更新)は行ってよい。
  行ったら報告に一覧で書く
- 目的(何を守っているか)を変える書き換え・削除・skip はしない。必要なら止めて理由を報告する

## 検証(報告前に自分で回す)
<機械チェックのコマンド。例:
 uv run --project tools/prepublish-checks python tools/prepublish-checks/note_gate.py <draft>
 該当 pytest / check_links.py など>
「これが通るまで直せ。通らない場合は理由を報告に書け」

## 報告フォーマット(これだけ返す。ログ・全文は貼らない)
- 変更したファイル一覧
- やったことの要点(3〜6行)
- 追従させた既存テストの一覧(あれば)
- 実測していない主張(「〜のはず」「仕様上〜」)は「未実測」と明記
- 未解決/不確実な点(自己申告)
```

### ブリーフの原則

- **既存テストの扱いを区分して渡す。** 「既存テストを書き換えるな」と一律に禁じると、実装変更に
  伴う文字列追従だけで subagent が赤いまま止まり、「書き換えてよいか」の確認往復が増える。
  目的不変の追従は許可して一覧報告、目的の変更は停止、と分ける。

- **受け入れ基準は検証可能な形で**書く。「きれいにして」ではなく「重複関数を統合し、pytest が緑」。
- **前提はパスで渡す**(全文貼り付けは親のトークンを食う。subagent に読ませる)。
- **機械チェックを同梱**し「通るまで直せ」と書く。往復の多くはこれで消える。
- **報告は圧縮**を指示。ツール出力・ファイル全文・思考ログを親に返させない。

### 作業の種類ごとにブリーフへ足すもの

**見た目・レイアウト(CSS・画面配置)の修正**

subagent に「推論で CSS を直させ、親が実ブラウザで見て差し戻す」と往復が増える
(実例: スマホ幅の崩れで 3 往復。media query の重なり・flex の内容幅を subagent は仕様からの
推論で直し、実測していなかった)。

- **原因の特定は親が実測で済ませてから委譲する。** computed style と要素の box の数値で「どの規則が
  勝っているか」をブリーフに書く。仮説のまま渡さない。
- **受け入れ基準を組合せごとの期待値で書く。** 例: 「幅 390 / 800 / 1200 / 1440 × ライト / ダーク ×
  展開 / 畳んだで、A と B の box(x, y, w, h)が一致」。報告された 1 画面だけを基準にしない。
- **兄弟画面(同じ部品を使う別画面)も範囲に入れる。** 片方だけ直すと次の報告で戻ってくる。
- subagent が実ブラウザを使えないなら、報告で「未実測」を明記させ、**親がその組合せを実測してから**
  合格にする。

**判定・名前・クラスの置き換え**

- 旧参照の `grep` 結果(全件)をブリーフに付け、受け入れ基準を「全件を置換済み or 残す理由を報告」に
  する。1 箇所の取り残しが本番の不具合になる。

**長い作業(利用上限・中断に備える)**

- 区切り(1 つの受け入れ基準)ごとに作業ツリーを整合した状態で止めるよう指示する。subagent が
  利用上限などで途中終了しても、親が残りを引き取れる。

## 親(Fable/Opus)のレビュー手順 ※安く済ませる

subagent の自己申告は信用しない。ただし**元資料を読み直さない**。成果物と機械チェックで見る。

1. **機械チェックを親が1回回す**(subagent が「通った」と言っても再実行して裏を取る)。
2. **diff / 生成物の該当箇所だけ**を見る(`git diff`、対象ファイルの変更部)。全読みしない。
3. 照合する観点:
   - 受け入れ基準の**全項目**を満たすか
   - **範囲外**を触っていないか(消してはいけないものを消していないか)
   - 破綻・文字化け・**捏造**(ありもしない事実/リンク)・規約違反はないか
   - 「できました」の**裏が取れる**か(取れない主張は未達扱い)
   - **「未実測」「〜のはず」の主張**を親が実測したか(見た目の修正は、報告された組合せ以外も)
4. **判断が要る領域は専用スキルに委ねる**。このリポジトリなら:
   - 記事の下書き → `note-reviewer` スキル(声・事実・X告知・特定リスク)
   - Python の設計/規約 → `python-dev-workflow` スキル
   車輪の再発明をしない。

## 再委譲(SendMessage で同じ subagent へ)

修正は**新規 subagent を立てず**、`SendMessage`(to: その agentId / 名前)で差し戻す。
温まった文脈が残っているので cold start を再び払わずに済む。

差し戻しメッセージの形:
```
レビュー結果、以下が未達。直して再報告して:
- <受け入れ基準N> が未達。証拠: <diff の該当/チェック出力>。期待: <具体的にどうあるべきか>
- <ファイル:行> の <問題> を <こう> 直す
（それ以外は良好。触らないで）
```

### 往復の打ち切り

- **原則2往復まで。** 2回直して基準に届かないなら深追いしない:
  - (a) 親が自分で仕上げる(残りが小さいなら手戻りより安い)
  - (b) ブリーフの設計ミスを疑い、基準を書き直して出し直す
  - (c) そのタスクは実は「判断が要る」= 委譲不適だった、と見て親が引き取る
- 往復のたびにトークンを使う。ズルズル差し戻すのは節約目的に反する。

## 完了報告(ユーザー向け・1〜2行)

「何を・どのモデルに委譲し・何を直させたか」を短く伝える。
例:「20ファイルの一括リネームを Haiku に委譲、レビューで2件の取りこぼしを差し戻して解消。」
