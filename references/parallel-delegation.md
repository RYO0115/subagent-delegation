# 複数 subagent の並列委譲(時間とトークンの釣り合い)

委譲すると決めた作業(when-to-delegate.md の ROI テストを通ったもの)を、**1 体に渡すか、
分割して複数体を同時に走らせるか**の判断基準。

並列化で縮むのは**待ち時間**で、増えるのは**トークン**。
直列なら「各作業の時間の合計」かかるところが、並列なら「一番長い作業+統合・レビュー」で済む。
その代わり、1 体増やすごとに次のコストを払う:

| 追加コスト | 中身 | 目安 |
| --- | --- | --- |
| cold start | ブリーフ作成+規約・関連コードの読み直し | 1 体あたり 2〜5 万トークン・数分 |
| 契約の確定 | 分割境界(ファイル所有・DOM の id・JSON の形・関数シグネチャ)を親が先に決める | 親の数分 |
| レビュー | 親が diff を 1 体ずつ見る(レビューは直列) | 1 体あたり親の数分 |
| 統合 | 境界の食い違い・衝突の解消、全体テスト | 境界が曖昧だと往復になり最大のコスト |

目安の数値は環境で変わる。実際の `subagent_tokens` / `duration_ms`(完了通知に出る)を見て補正する。

## 判定(上から順に。1 つでも No なら分割しない = 1 体に渡す)

1. **独立しているか?**
   - 触るファイルが重ならない(**ファイル所有を排他にできる**)。同じファイルを 2 体で編集しない。
   - 順序依存が無い(A の結果を見ないと B を書けない、ではない)。
   - 境界の契約を**着手前に親が決め切れる**。決め切れないなら、先に契約だけを決める段を置くか、分割しない。
2. **1 片が十分に大きいか?**
   - 分割後の各片が単独で **10 分以上 / 数ファイル以上**の作業量を持つ。
   - 片の作業量が cold start と同程度以下なら、分割は損(1 体にまとめて渡す)。
3. **縮む時間が見合うか?**
   - 見込みの短縮が **10 分以上、かつ直列時間の 3 割以上**。
   - 最長の片が全体の大半を占める(例: 20 分+3 分+2 分)なら、並列にしても短縮は小さい。
     小さい片は 1 体へまとめるか、親が自分でやる。
4. **共有資源を分けられるか?**
   - ビルド出力先(`--out`)、ローカルサーバのポート、一時ファイルを片ごとに別にできる。
   - DB・preview・push のような共有資源に書く片は 1 体だけ。push / commit は親が統合後に行う。

全部 Yes なら並列にする。ユーザーが明示したときは重みを変える:
「急ぎ」なら 3 の閾値を下げてよい。「トークン節約」なら 1 体を基本にする。

## 上限

- **同時に走らせるのは原則 3 体まで。** 親のレビューは直列なので、それ以上は待ちが親側に移る。
  利用上限(HTTP 429)に同時に当たると全員が途中で止まるリスクも増える。
- 同じ種類の機械作業(大量ファイルの定型置換など)は、原則 1 体にまとめる。
  分割するのは、1 体では 30 分を超える量で、かつファイル群で排他に切れるときだけ。

## 分割のしかた

- **層・ファイル種別で切る**のが最も安全。例: Python / ビルド側 と 生成 JS / CSS / テンプレート側。
  (実績: 両方へ「相手のファイル名を禁止リスト」として渡し、衝突なく並行できた)
- **調査は問いごとに切る。** 独立した問い(別サブシステム、別のログ、別の資料)は Explore を並べる。
  結論だけを返させ、突き合わせは親がやる。
- **独立した sub-issue で切る。** 触るファイルが重ならない不具合修正は並べてよい。
- 切ってはいけない例:
  - 同じファイル(例: 1 つの CSS)を複数体で編集する
  - 見た目の修正で、規則が互いに影響し合うもの(カスケード・レイアウト)
  - 設計 → 実装のように順序依存があるもの(段に分けて直列にする)

## ブリーフに足すもの(並列時)

各 subagent への brief-and-review.md の雛形に、次を加える:

- **所有ファイル**(触ってよい)と、**他の片の所有ファイル**(触ってはいけない)。
- **親が決めた契約**(id・JSON の形・関数シグネチャ)。契約を変えたくなったら、変えずに止めて報告。
- **片専用の出力先・ポート**(`--out <scratchpad>/<片名>` など)。
- **commit / push はしない**(統合は親)。
- 自分の片に関係するテストだけを回して報告する。全体テストは統合後に親が回す。

## 統合とレビュー

1. 完了した片から順にレビューする(全員を待たない)。差し戻しは同じ subagent へ SendMessage。
2. 全片が揃ったら、親が全体テスト・lint・(画面なら)確認マトリクスを 1 回回す。
3. 境界で食い違ったら、どちらの片の問題かを決めてその subagent へ差し戻す。親が抱え込まない。
4. ユーザーへの報告に「何体に分けたか・分けた軸」を 1 行で書く。
