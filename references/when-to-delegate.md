# 委譲する / しないの判断(ROI基準とモデル選び)

このスキルの目的は**トークン削減**。だから「委譲できるか」ではなく「委譲したら**得か**」で決める。
fresh subagent は cold start(規約・文脈をゼロから渡し直す)コストを毎回払う。それを上回る
節約が見込めるときだけ出す。

## ROIテスト(3問すべて Yes なら委譲、1つでも No なら自分でやる)

1. **中間出力が大きいか?** — その作業は、大量のファイル読み・検索ヒット・試行錯誤ログを
   生むか? それらは親コンテキストに入れたくない量か?
   (Yes 例:30ファイル横断の一括置換、広いツリーの調査、長いログの読解。
    No 例:1〜2ファイルの数行修正 → 中間出力が小さく、隔離する意味が薄い。)
2. **成果物は小さくまとまるか?** — 返ってくるのが diff・表・要点リストなど**コンパクト**か?
   (Yes ならレビューも安い。No=大きな成果物を全部読み直すなら節約が消える。)
3. **賢さより手数の作業か?** — 判断・センス・文脈の機微が要らず、**基準を渡せば正解が一意**に
   決まるか?(Yes なら Sonnet/Haiku で足りる。No=設計判断・著者の声・事実の真偽は親が持つ。)

## 委譲が「得」な作業(典型)

- **一括の機械編集**:命名変更・整形・定型パターンの適用を多数ファイルに。→ Haiku。
- **広域の探索/調査**:「どこで何が使われているか」を広く調べ、**結論だけ**返す。→ Explore(Sonnet)。
- **長文の読解・要約**:長いドキュメント/ログ/複数ソースを読んで、要点・表・claim→根拠に圧縮。→ Sonnet。
- **仕様からの定型生成**:はっきりした spec からボイラープレート・設定・テストの雛形を作る。→ Sonnet。
- **明確な受け入れ基準のあるリファクタ**:「この関数を分割・重複を統合、テストが緑のまま」。→ Sonnet。
- **緑になるまで回す系**:テスト/リンタ/ビルドを回して**通るまで**直させ、結果だけ返す。→ Sonnet。

## 委譲が「損」な作業(自分でやる)

- **数ファイルの小改修**:cold start のブリーフ+再説明のほうが高い。
- **一問一答・短い確認**:往復オーバーヘッドが本体を上回る。
- **強い文脈依存**:直前までの会話・暗黙の前提が効いていて、ブリーフに書き起こすのが高くつく作業。
- **判断・センスの中核**:著者の声(knowledge/voice.md)、事実の断定、アーキテクチャの意思決定、
  トレードオフの選択。ここを安いモデルに出すと品質が落ち、結局親が全部やり直す=最も高い。
- **既に親が Sonnet/Haiku**:下へ委譲しても節約にならない。
- **自分が subagent(fork 含む)**:多段委譲しない。その場で実行。

## モデルの選び分け

| 作業の質 | モデル | 例 |
|---|---|---|
| 純粋に機械的(判断ゼロ) | **Haiku** | 定型置換、整形、単純抽出、リネーム、フォーマット統一 |
| 少し推論・取捨選択が要る | **Sonnet** | リファクタ、spec からの実装、要約の要点選び、テストを緑にする |
| 判断・センス・文脈の機微 | **委譲しない(親=Fable/Opus)** | 著者の声で書く、事実の真偽判定、設計判断 |

迷ったら **Sonnet**。Haiku で品質が足りず往復が増えるより、最初から Sonnet のほうが結果的に安いことが多い。

## 規模の目安

- 1体の subagent に**まとまった塊**を渡すのが基本。同種の機械作業は原則 1 体にまとめる
  (briefing の重複コストで元が取れない)。
- 分割して複数体を並列に走らせるかは [parallel-delegation.md](parallel-delegation.md) の判定で決める
  (独立性・1 片の大きさ・縮む時間・共有資源の分離。最大 3 体)。
